# 加密协议设计

## 1. 符号与编码

| 符号 | 含义 |
|---|---|
| `S_pub` / `S_priv` | 服务器 RSA-2048 公钥 / 私钥 |
| `C_pub` / `C_priv` | 客户端每次登录临时生成的 RSA-2048 公钥 / 私钥 |
| `K_room` | 房间会话密钥，AES-256，32 字节随机 |
| `K_arc` | 归档主密钥，AES-256，32 字节随机 |
| `E_rsa(pk, m)` | RSA-OAEP(SHA-256)，输出 base64 |
| `E_aes(k, m, aad)` | AES-256-GCM，12 字节随机 IV + 16 字节 tag，输出 `{iv, ct, tag}` 均为 base64 |
| `b64` | 所有二进制字段统一 base64 字符串 |

算法参数集中在 `shared/protocol.js`：`RSA_BITS=2048`、`AES_KEY_BYTES=32`、`IV_BYTES=12`、`TAG_BYTES=16`、`HASH=SHA-256`、`OAEP=RSA-OAEP/SHA-256`、`SIG=RSA-PSS/SHA-256`。

## 2. 信任模型（务必理解）

**本方案是「密钥分发中心（KDC）」模型，不是严格的端到端加密。**

- `K_room` 由**服务端生成**并在内存中持有，用于给各成员封装交付。因此服务端在技术上具备解密实时消息的能力。
- 这是需求「服务器保留聊天数据，且只有服务器端可查看归档」的必然结果：服务端必须能解密归档。
- 真正的机密性边界是：
  1. **网络旁路者 / 代理 / 中继**只能看到 AES-GCM 密文，无法读取消息；
  2. **磁盘数据**以 `K_arc` 加密，`K_arc` 又被 `S_pub` 封装，只有持 `S_priv` 者能解封，数据库文件单独泄露不泄露聊天内容；
  3. `K_room` 与 `K_arc` 的**明文都不落盘**，仅存在于服务端进程内存，进程退出即消失（重启后从 `S_priv` 解封 `K_arc` 恢复归档能力）。
- 若未来需要真 E2EE：改由**房间创建者的客户端**生成 `K_room`，服务端仅代转发"用各成员 `C_pub` 封装的密钥包"，服务端不再持有明文；代价是服务端无法解密归档，与当前需求冲突，需产品层面重新确认。

## 3. 服务端启动

1. 若 `server/data/keys.json` 不存在：生成 RSA-2048 密钥对、生成 `K_arc`。
2. 用 `S_pub` 对 `K_arc` 做 RSA-OAEP 封装，写入 `keys.json`（字段 `wrappedArchiveKey`）。
3. `S_priv` 以 PEM 形式写入 `keys.json`（本地文件权限依赖操作系统；生产环境应改为口令派生密钥加密）。
4. 运行时用 `S_priv` 解封得到 `K_arc`，仅驻留内存。
5. 打印 `S_pub` 的 SHA-256 指纹（前 16 hex），供客户端人工核对，防中间人替换公钥。

> 注意：本版无 CA 证书体系，首次连接属于 "trust on first use"。局域网场景下通过核对指纹或面对面确认公钥指纹来防 MITM。

## 4. 注册与身份认证（非对称）

```
Client                                      Server
  |--- HELLO {} -------------------------------->|
  |<-- WELCOME {pubKey, fingerprint, challenge, ts, salt} --|
  |                                               | 记录 challenge -> 会话
  | 生成 C_pub/C_priv                             |
  | browserId = 指纹(UA|屏幕|Canvas|WebGL|时区|语言) + localStorage 随机盐
  | plain = {v, username, browserId, ts, nonce, challenge, clientPub}
  | digest = SHA256(username|browserId|ts|nonce|challenge)
  | sig = RSA-PSS 签名(C_priv, digest)
  | blob = 混合加密(S_pub, JSON({...plain, sig}))
  |--- REGISTER {blob} ------------------------->|
  |                                               | 用 S_priv 解密
  |                                               | 校验 challenge / ts(±60s) / nonce 唯一 / 签名
  |                                               | UID = SHA256(browserId|ts|salt|challenge)
  |                                               | 生成 K_lobby（大厅会话密钥）
  |                                               | wrapped = E_rsa(C_pub, base64(K_lobby))
  |<-- REGISTERED {uid, wrappedLobbyKey, iv, tag, serverInfo} -|
  | 用 C_priv 解封得 K_lobby                     |
```

校验失败统一返回 `ERROR`，不区分具体原因，避免信息泄露。

**注册包必须用混合加密**：`clientPub`（PEM 约 450 字节）+ `sig`（base64 约 344 字节）远超 RSA-2048/OAEP-SHA256 的 190 字节明文上限，因此不用 RSA 直接加密注册包，而是：

```
K_reg = CSPRNG(32B)
blob = {
  wrappedKey : E_rsa(S_pub, b64(K_reg)),
  iv, ct, tag: E_aes(K_reg, JSON(inner), aad="chatroom-register-v1")
}
```

服务端先用 `S_priv` 解封 `K_reg`，再 AES-GCM 解密并校验认证标签。这与「会话密钥由非对称算法封装交付」是同一套模式。

**每次登录全新用户**：`ts` 与 `nonce` 每次都不同，`salt` 每次连接由服务端新生成，因此 `UID` 必然变化；客户端不持久化任何身份材料。

## 5. 会话密钥交付

- 每个房间（含大厅、每个私聊会话）独立 `K_room`，互不派生，一个房间泄露不影响其他房间。
- 成员加入房间时，服务端取该成员注册时上报的 `C_pub`，计算 `E_rsa(C_pub, b64(K_room))`，通过 `ROOM_JOINED` / `KEY_DELIVERY` 单独下发。
- 客户端用 `C_priv` 解封，缓存在内存 `Map<roomId, CryptoKeyBytes>`；切换页面即失效。
- 预留 `KEY_ROTATE` 消息类型：成员退出时轮换 `K_room` 并向剩余成员重新封装（本版仅预留字段，未启用，见需求 5）。

## 6. 消息加密

```
toSend = { text, kind: 'text', replyTo? }
aad = `${roomId}|${uid}|${seq}|${ts}`
{iv, ct, tag} = E_aes(K_room, JSON(toSend), aad)
payload = { room: roomId, seq, iv, ct, tag, ts }
```

- `iv` 每条消息由 CSPRNG 重新生成，禁止复用。
- `seq` 每房间每客户端单调递增，服务端校验 `seq > lastSeq[uid][room]`，防止重放。
- 服务端**不解密** `ct`，只按 `room` 广播给房间内其他成员，并把该 envelope 交给归档模块。
- 接收方用本地 `K_room` 解密，校验 GCM tag 失败则丢弃并提示「消息校验失败」。
- 渲染一律使用 `textContent`，禁止 `innerHTML`，从源头杜绝 XSS（因此无需引入 DOMPurify）。

## 7. 归档加密（只有服务器端可查看）

```
服务端收到 payload
  -> plaintext = D_aes(K_room, payload)        // 内存中的 K_room
  -> archived  = E_aes(K_arc, plaintext, aad=room|seq|ts)
  -> INSERT INTO messages(room, from_uid, from_name, seq, iv, ct, tag, aad, ts)
```

- 归档与传输使用**不同密钥**，传输密钥泄露不影响历史归档。
- `K_arc` 明文只在内存；磁盘上只有 `E_rsa(S_pub, K_arc)`。
- 服务端配置界面查看历史时：用 `S_priv` 解封 `K_arc`（或直接使用内存副本）→ 解密 `ct` → 展示。
- 数据库表：`rooms`、`messages`、`members`、`server_meta`；全部业务字段为密文或不可逆标识。

> 语义纠正：原始需求写「通过服务器端私钥加密」。RSA 中用私钥"加密"实质是签名，任何持公钥者都可还原，不提供机密性。正确做法是**用服务器公钥加密/封装**，私钥解密，本设计按此实现。

## 8. 代理与中继

- 浏览器 JS 无法为 WebSocket 指定 SOCKS5 代理；`ws://` 只能走系统代理。
- 客户端填写「代理/中继地址」后切换为 HTTP 轮询模式：
  - `POST {proxy}/relay`，body 为 `{clientId, envelope?}`，`envelope` 是**已加密的密文包**；
  - 服务端把该请求视作对应虚拟 Session 的入站消息，并把积压的下行 envelope 放进响应 `messages` 数组返回；
  - 客户端以约 300ms 间隔发空 `envelope` 拉取下行。
- 中继（Nginx / 自建 / 服务端内置 `/relay`）全程只见密文，不构成新的信任方。
- 未填写代理时走原生 WebSocket，操作系统代理自动生效。

## 9. 已知限制

- 无证书体系，首次连接需人工核对公钥指纹。
- 无前向保密：若攻击者同时取得 `S_priv` 与录制的历史传输流量，可回溯解密（因为 `K_room` 由 `S_pub`/`C_pub` 封装传输）。启用 libsodium X25519 + 房间密钥轮换可缓解。
- 归档明文可由服务端读取，这是需求本身的取舍，部署时应把服务端机器视为可信节点。
- 时间戳依赖系统时钟，允许 ±60s 偏差。
