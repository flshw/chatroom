## 二、S1 · 性能实测与容量结论

### 实测方法

新增 `GET /api/metrics`（公开，仅内存/CPU/计数，不含任何密钥或消息内容）。`tools/benchmark.js` 用 `CHATROOM_DATA_DIR` 隔离实例，按 0/25/50/100/150 在线梯度采样并做**线性回归**求每用户内存斜率；归档阶段按消息条数多次采样拟合；广播阶段轮询到归档计数达标才计时。原始数据保存在 `logs/benchmark-2026-11-14.json`。

### 核心数据

| 指标 | 实测值 |
|---|---|
| 空载 RSS / Heap | 75.35 MB / 11.98 MB |
| 每在线用户增量 | **RSS +222.52 KB、Heap +95.82 KB**（两次平均约 210 KB RSS / 88 KB Heap） |
| 单次非对称注册 CPU | **107.3 ms/次**（2 核约 18 次/秒） |
| 注册握手 node-forge → node:crypto | 29.84 ms → 1.21 ms（**24.7×**） |
| 每条归档消息内存增量 | **3.738 KB/条**，保守按 4～5 KB 估算 |
| 大厅广播 | 180 人 / 100 发送者 / 17 900 帧，CPU 641 ms ≈ **36 µs/帧** |

### 2 核 4 G Ubuntu 26.04 结论

| 场景 | 建议在线上限 | 主约束 |
|---|---|---|
| 开箱即用（默认 ulimit、单大厅、无归档清理） | **300～500 活跃 / 约 900 连接** | `LimitNOFILE=1024`、大厅 O(N²) |
| 基础调优（fd 65535 + 归档滚动 + 引导分房间） | **800～1 200 稳态，峰值 1 500** | 大厅广播 CPU |
| 全员只在大厅、1 条/分钟 | 约 1 600 | CPU |
| 原地优化（原生加密 + 归档滚动 + 2 进程集群） | 3 000～5 000 | 内存/GC |
| Go / Rust 重写 + 磁盘存储 + 房间分片 | 1 万～5 万 | 业务设计与网络 |

**直接回答**：当前 v4 实现，先调高 `LimitNOFILE` 并开启归档滚动清理后，稳态建议 **800～1200 人在线**，峰值 1500；若全部挤在大厅且发言活跃，降到约 1000～1600。内存可支撑上万，但 CPU 的 O(N²) 广播与注册握手先到顶。

> 本机为 Windows x64（Node v22.22.2），**未在真实 Ubuntu 26.04 实机测量**；Linux 的 epoll / malloc 通常略优，结论按保守口径外推，已在文档中如实标注。Linux 特有的硬约束是 systemd `LimitNOFILE` 与归档常驻内存。

## 三、S2 · 语言与架构选型

**结论：换 Rust/Go 确实能提高上限，但当前天花板不是「JS 慢」，而是三个具体设计问题**——纯 JS `node-forge` 做 RSA、sql.js 整个数据库常驻内存、大厅广播 O(N²)，外加 `LimitNOFILE=1024`。不改存储、不分房间、不调 fd，用 Rust 重写仍会卡在约 1000～1600 在线。

按性价比推荐的三种方式：

| 方案 | 做法 | 容量 | 工期 | 风险 |
|---|---|---|---|---|
| **A · Node 原地优化（首选）** | `node:crypto` 替换 forge 热点（密文/PEM 格式完全兼容）、归档滚动保留、2 进程 `cluster` 按房间粘性路由 | 3 000～5 000 | **3～5 人日** | 最低，客户端零改动，154 项回归可复用 |
| **B · Go 单二进制** | `net/http` + goroutine/websocket + modernc sqlite/bbolt + 原生 crypto | 1 万～3 万 | 12～18 人日 | 中：OAEP/PSS 参数需与浏览器客户端逐字节对齐 |
| **C · Rust 全异步栈** | tokio + axum + tokio-tungstenite + rusqlite + ring + dashmap | 3 万～10 万 | 20～30 人日 | 中高：密码学互通与协议对齐约占 1/3 工期 |

本项目的真实规模是局域网几十到几百人，**方案 A 足矣**；只有明确上千在线才进 B，C 仅在产品化且有 Rust 工程能力时合理。任何重写都必须保留 `/api/*` 契约与 `shared/protocol.js` 消息类型，否则已分发的单文件客户端会全部失效。

## 四、S3 / S4 · 门户页与免下载聊天

### 新增端点

| 端点 | 说明 |
|---|---|
| `GET /welcome` | 客户端下载页与使用说明：在线聊天 / 下载双入口、`/api/client-info` 展示 SHA-256 与体积、服务器地址与公钥指纹、快速开始、身份 XML 保存/导入/切换步骤、功能一览、FAQ、管理台入口 |
| `GET /download/chatroom.html` | 带 `Content-Disposition: attachment` 的单文件下载 |
| `GET /api/client-info` | 文件名、字节数、SHA-256、版本、能力集、服务器 IP/端口与指纹 |
| `GET /` | **本来就托管 `server/public/chatroom.html`**，局域网浏览器直接打开即在线聊天，无需下载 |

### 可行性结论（`docs/13`）

- **A 直接在线聊天**：可行且已具备；私钥仅在浏览器内存，服务端只存公钥。
- **B 门户页 + 引导**：本轮实现（`/welcome`）。
- **C 服务端代管身份 XML 并代登录**：**明确不采用**。注册协议要求客户端用私钥对挑战码做 RSA-PSS 签名以证明「私钥仍在你手里」；把 XML 交给服务端解密等于让管理员可冒充该用户发起私聊，直接破坏 E2EE 边界。
- 导入 XML 在 Web 端纯浏览器 API 即可完成（`<input type=file>` → `DOMParser` → 可选 PBKDF2 解密 → `privateKeyFromPem` → 挑战签名），服务端零改造，链上仍只存公钥。

## 五、S5 · 机器人系统

`server/src/bots.js`（`BotManager`）为本轮新增核心模块：

- **持久身份池**：首次启动向 `identities` 表写入 1000 条机器人身份（`is_bot=1`、`permanent=1`），并在身份哈希链写 `bot_pool_init` 区块；重启不重复生成。
- **在线轮换**：默认 10～20 个在线，每 25 s 刷新一次，40% 概率随机替换部分在线机器人；`BotSession` 继承 `Session`，不消费服务端推送，退出不广播 notice、不写普通断开日志。
- **自动回复**：`Hub.registerMessageHook(fn)` 在普通房间消息归档后回调；机器人按 `replyProbability=0.6` 回复真人、`ambientProbability=0.35` 主动闲聊；发言用 `room.key` 生成与真人一致的 AES-GCM 密文并走 `hub.handleEnvelope()` 正常归档/广播路径，客户端可正常解密。
- **E2EE 边界**：机器人**不进入**端到端加密房间，服务端 `room.key=null` 时无法产生明文，不存在「机器人旁听私聊」。
- **可管理**：管理页新增「机器人」面板，可开关、调整池容量/在线上下限/刷新间隔/回复概率、立即轮换、手动让某个在线机器人发言；配置写入身份哈希链 `bot_config` 区块并持久化，软重启后保留。

| 管理 API | 作用 |
|---|---|
| `GET /api/admin/bots` | 配置 + 在线机器人清单（uid/昵称/房间） |
| `POST /api/admin/bots` | 修改配置（`enabled`/`poolSize`/`minOnline`/`maxOnline`/`refreshMs`/`autoReply`/概率） |
| `POST /api/admin/bots/refresh` | 立即轮换 |
| `POST /api/admin/bots/say` | 手动发言（未指定或已下线的 uid 自动回退到当前在线机器人） |

管理页同时增加「显示机器人身份」开关、用户表格机器人标记、概览区分在线真人/在线机器人。

## 六、S6 · 多房间同开

- **协议**：`MAX_ACTIVE_ROOMS=3`、`MAX_ROOM_MESSAGES=400`、新增错误码 `E_ROOM_LIMIT`；`shared/protocol.js` 为权威源，构建时同步到 `server/src/protocol.js`。
- **服务端**：`Hub` 在 ROOM_CREATE / ROOM_JOIN 前检查 `user.rooms.size`，超限返回 `E_ROOM_LIMIT` 并提示「请先关闭一个房间标签」；历史按房间分别读取，房间之间广播与归档严格隔离；`stats()` 增加同时在房间数。
- **客户端**：`openRooms[]` + `roomState{id:{messages,members,unread,historyLoaded}}` 独立维护每个房间的消息、成员、未读与历史；顶部横向房间标签条可切换/关闭，未读角标提示，最多 3 个（大厅 + 2 个房间）。

## 七、C1 / C2 / C3 · 客户端改造

### C1 移动端 H5 与身份管理

`client/src/style.css` 增加 `@media(max-width:760px)`：`100dvh` 高度、`viewport-fit=cover` + `env(safe-area-inset-*)` 安全区、输入框 `font-size:16px` 防 iOS 自动缩放、侧栏改抽屉（遮罩 + 滑出）、触摸目标 ≥44 px、房间列表改横向滚动标签。局域网 `http://` 非安全上下文，Service Worker 不可用，故**不做 PWA 离线缓存**；移动端保留点击选取文件（`accept=".png,.pdf,.zip"`）。

身份管理采用**浏览器内身份库 Vault**（`localStorage`，键 `chatroom-identity-vault-v4`），不依赖文件系统：

| 能力 | 实现 |
|---|---|
| 管理 | 条目列表（昵称/UID/服务器/创建时间）、重命名、删除 |
| 导入 | 文件选择读入 XML → 完整性校验 → 入库；也可临时导入不入库 |
| 导出 | Blob 下载 `.xml`，可经 Web Share 分享到其它设备 |
| 快速登录 | 顶栏「切换身份」→ 选条目 → 断开旧连接 → 恢复该身份 → 挑战签名重连 |
| 本地加密 | 加密身份切换时输入口令（PBKDF2 + AES-GCM），口令**只存页面内存**，不落盘 |

> 未采用 WebAuthn/Passkey（需 HTTPS）、云端身份同步（违背零公网依赖且交出私钥）、静默写当前目录 XML（浏览器沙箱禁止）、二维码承载完整 XML（私钥 PEM 约 1.7 KB，过大且暴露在屏幕）。跨设备迁移的**唯一可移植载体仍是导出 XML**。

### C2 在线切换用户

`useIdentity(entry)` 统一处理断开 → 解析（必要时索要口令）→ 设置 `state.identityFile` → 重连；服务端 ADR-012 的单会话接管语义保证切换后不残留旧会话状态。

### C3 拖拽上传

`wireDrop()` 监听 `dragenter/dragover/dragleave/drop`，用 `depth` 计数避免子元素抖动，显示全屏投放覆盖层；取 `e.dataTransfer.files[0]` 后复用既有链路：类型白名单 png/pdf/zip、≤8 MB、AES-256-GCM 加密后上传，png/pdf 仍可在聊天室预览，zip 下载。

## 九、安全边界（v4 未放宽）

1. 服务端身份链上**只存公钥**，用户私钥仅在客户端 XML / 浏览器内存；机器人身份同样不上传私钥到任何外部。
2. 私聊仍是真 E2EE：房间密钥由客户端生成并用双方公钥封装，服务端 `room.key=null`，只转发与存储密文；管理员只能看元数据。
3. 机器人不进入 E2EE 房间，无法获得私聊明文。
4. 门户页展示服务器公钥指纹要求用户核对；`/api/metrics` 不暴露密钥、消息或身份内容。
5. 拖拽上传与移动端选取共用同一套白名单、大小限制和 AES-GCM 加密，不新增明文通道。

## 十一、已知限制 / 后续建议

1. **归档无限增长**：sql.js 全库常驻内存，必须实现滚动清理（P0），否则长期运行会 OOM——这是任何语言重写前都该先做的事。
2. **`LimitNOFILE`**：Ubuntu systemd 默认 1024，约 1000 连接即 `EMFILE`；部署时务必设 `LimitNOFILE=65535`。
3. **注册风暴**：2 核约 18 次注册/秒，1000 客户端同时重连约需 56 秒；建议客户端加指数退避。
4. **Linux 未实机验证**：跨平台结论基于静态扫描 + 独立目录等价实测，若要在 Ubuntu 26.04 正式上线，建议按 `docs/09` 的 systemd 步骤实跑一次。
5. **身份库按浏览器隔离**：`localStorage` 跨浏览器/设备不共享，跨设备迁移仍靠导出/导入 XML。
6. 容量与语言选型属于评估与建议，**本轮未实施**方案 A/B/C 的代码改造；如需落地，优先做 P0/P1 四项（详见 `docs/11` 第 5 节）。
