# 架构决策记录（ADR）

## ADR-001：放弃「单个 HTML 同时充当服务器」的设想

- **背景**：v1 方案要求一个独立 HTML 文件同时具备服务端与客户端能力，显示 IP 与端口等待接入。
- **事实**：浏览器（含 `file://` 页面）没有 TCP `listen` 能力，可用 API 中 WebSocket / fetch / WebRTC 均为**主动连接方**。WebRTC DataChannel 虽可点对点，但仍需信令且不使用「IP + 端口」语义。
- **结论**：该设想在纯浏览器环境不可实现。用户已于 2026-11-14 确认忽略此项。

## ADR-002：服务端与客户端分离开发（v2，当前方案）

- **决策**：服务端独立为 Node.js 程序，客户端为纯前端页面。
- **收益**：
  - 服务端可真正监听 TCP 端口、显示内网 IP、等待接入；
  - 客户端无需内嵌服务内核，代码量与体积大幅下降，UI 更简洁；
  - 两端共用 `shared/protocol.js` 与同一套加密实现（node-forge 可跨 Node/浏览器运行）。
- **代价**：服务端机器需具备 Node.js 22 运行时；分发从「一个文件」变为「一个服务端目录 + 一个 HTML 客户端」。
- **缓解**：服务端同时静态托管客户端页面，用户只需访问 `http://<IP>:<端口>` 即可得到客户端；`client/dist/chatroom.html` 仍保持单文件可双击运行。

## ADR-003：加密实现选用 node-forge 而非 Web Crypto

- **事实**：`crypto.subtle` 仅在安全上下文可用；局域网 `http://192.168.x.x:<port>` **不是**安全上下文，`file://` 虽在部分浏览器算可信来源但行为不一致。
- **决策**：核心加解密统一用 `node-forge`（纯 JS，任意上下文可用），Web Crypto 仅作为可选加速（当前版本未启用，以保证行为一致）。
- **备选**：libsodium-wrappers（X25519 密封盒 / 前向保密）作为后续增强，代价是 WASM 体积约 +250 KB。

## ADR-004：归档使用「公钥封装」而非「私钥加密」

- **事实**：用私钥「加密」在 RSA 语义上是签名，任何持有公钥者都可还原内容，不提供机密性。
- **决策**：归档主密钥用**服务器公钥** RSA-OAEP 封装后落盘，聊天记录用该主密钥 AES-256-GCM 加密；只有服务器私钥能解封，满足「只有服务器端可查看」。
- **附加**：归档主密钥仅存在于服务端进程内存，配置文件与数据库中只存被封装后的密文。

## ADR-005：微型数据库选用 sql.js（SQLite WASM）

- **理由**：真 SQL 能力、纯 JS/WASM 无原生编译、服务端与浏览器均可运行、数据库可直接导出为单文件；避免 `better-sqlite3` 等需要 native build 的依赖带来的安装失败风险。
- **持久化策略**：内存 SQLite + 变更后防抖导出到 `server/data/chat.db`，进程退出前强制落盘。

## ADR-006：代理支持采用「应用级密文中继」

- **事实**：浏览器 WebSocket 无法在 JS 中指定 SOCKS5 代理；`ws://` 只能走系统代理设置。
- **决策**：客户端提供可选「代理/中继地址」输入。填写后，客户端把**已加密的密文包**以 HTTP POST 发给中继，由中继转发到服务端；中继全程只见密文，不构成额外的信任方。
- **服务端内置**：`POST /relay` 端点可作为同网段内最简单的中继；也可对接自建反向代理（Nginx / Caddy）。
- **系统代理**：用户不填代理时，浏览器自动使用操作系统代理配置，无需代码介入。

## ADR-007：每次登录全新身份 vs 历史记录

- **冲突**：身份码包含时间戳与随机盐，每次登录必然是全新 UID，无法按 UID 关联历史。
- **决策**：历史消息按**房间**归档（而非按用户），服务端配置界面按房间解密查看；用户凭房间邀请码重新加入后可拉取该房间的历史密文并用当前会话密钥解密。
- **默认**：客户端进入房间时默认不自动拉取历史，避免新身份看到过往成员信息；可在配置界面开启。

## 已识别风险与处理

| 风险 | 处理 |
|---|---|
| `file://` 客户端 `Origin: null` 被 CORS 拦截 | 服务端对 `Origin: null` 放行，返回 `Access-Control-Allow-Origin: *` |
| `file://` 页面访问 `http://` 被混合内容策略拦截 | 优先推荐通过服务端托管地址访问；直连模式提供明确错误提示 |
| RSA 明文长度上限 | 只用于加密短小的密钥/注册摘要，消息体一律走 AES 混合加密 |
| 系统防火墙拦截端口 | 服务端启动时打印放行提示，`docs/09` 给出 Windows `netsh` 与 Linux `ufw`/`firewalld` 命令 |
| 浏览器指纹在无痕/隐私模式退化 | 指纹失败时回退到 `crypto.getRandomValues` 随机 ID + 时间戳，仍满足「每次登录全新」 |
| UDP/TCP 端口占用 | 端口可通过配置或环境变量修改，启动时检测并报错 |

## ADR-008：注册包与密钥交付统一采用混合加密（编码阶段修订）

- **发现**：编码与联调时确认，注册包含 `clientPub`（PEM 约 450 B）与 RSA-PSS 签名（base64 约 344 B），超过 RSA-2048/OAEP-SHA256 的 190 B 明文上限，无法用 `E_rsa(S_pub, inner)` 一次加密。
- **修订**：注册包改为 `K_reg` 随机 AES-256 密钥加密正文，`K_reg` 由服务器公钥 RSA-OAEP 封装；与房间会话密钥的封装交付是同一模式。
- **同步更新**：`docs/06-加密协议设计.md` 第 4 节、`docs/07-通信接口规范.md` 的 register 报文与 AAD 约定已按实现校正。
- **另修正**：forge 的 `publicKey.verify()` 需传字节字符串（`md.digest().getBytes()`）而非 `ByteBuffer`，否则 RSA-PSS 验签恒为 false；该问题在首轮冒烟测试中暴露并已修复。

## ADR-009：服务端目录必须自包含（跨平台部署阶段修订）

- **发现**：做「仅拷贝 `server/` 到空目录、换端口启动」的部署实测时报错 `Cannot find module '../../shared/protocol'`——4 个源文件引用了工作区根部的 `shared/protocol.js`，目录一旦单独分发即不可启动；日志目录也曾指向根部 `logs/`，在 Linux 只读父目录下会写入失败。
- **决策**：`server/` 目录作为唯一部署单元，自身必须完整可运行，不依赖工作区任何其他目录。
  - 新增 `server/src/protocol.js`，4 处 `require` 改为 `require('./protocol')`；
  - `tools/build-client.js` 以 `shared/protocol.js` 为权威源，每次构建自动向 `server/src/protocol.js` 同步字节一致的副本，避免协议常量分叉；
  - `main.js` 日志目录改为 `server/logs/`；启动横幅防火墙提示改为 Windows / Linux 通用。
- **验证**：仅含 `server/` 的独立目录在 8099 端口启动，健康检查、静态页、完整 22 项端到端测试全部通过。
- **意义**：这是 Windows / Linux 双平台可直接拷贝运行的前提，详见 `docs/09-服务端组件清单与跨平台部署.md`。

## ADR-010：v3 身份双轨制与「区块链」落地形态

- **冲突**：v2 的「每次登录全新身份」与 v3「保存用户信息方便重新登录」直接矛盾。
- **决策**：默认仍为临时身份；勾选保存身份文件或导入 XML 时登记为持久身份，注册包带 `resume:{uid,proof}`，服务端用链上公钥验 RSA-PSS 证明后恢复同一 UID。
- **区块链语义**：局域网单机没有多节点，PoW/共识/P2P 不增加信任。实现为**单节点许可式哈希链**：`prevHash + payload + hash + 服务器 RSA-PSS 签名`，落 `ledger_blocks` 表，提供 `verify()` 检出任何篡改。诚实标注不是公链。
- **安全底线**：服务端链上**只存公钥**，用户私钥只存在客户端 XML（可选 PBKDF2+AES-GCM 口令加密）。若服务端保存私钥，任何拿到服务器的人都能冒充用户。

## ADR-011：私聊真 E2EE，管理员只能看元数据

- **冲突**：需求「私聊只有双方可见」与「管理员查看私聊」、以及 v2「服务端加密归档可解密」严格冲突。
- **决策**：优先满足「只有双方可见」。私聊房间密钥由发起方客户端生成，用双方公钥分别 RSA-OAEP 封装成 `wrappedKeys` 提交；服务端 `room.key = null`，只转发/存储密文，不解密、不归档明文。管理员查看私聊只能得到发送人、时间、序号与密文长度。
- **代价**：换身份文件后无法解密该私聊的历史密文；服务端无法对私聊做内容审计。二者均为 E2EE 的必然结果。

## ADR-012：同一身份单会话接管（联调缺陷修复）

- **发现**：v3 端到端测试中，用同一持久身份再登录一次后关闭新连接，会错误地把前一个会话的用户状态从 `users` 表中删除，导致原连接之后所有操作返回「未注册」。
- **决策**：`Hub.onRegister` 检测到 uid 已在线时，通知并关闭旧连接，由新会话接管；`Hub.detach` 增加 `user.session === session` 判断，旧套接字关闭时不得清理已被接管的状态。
- **验证**：改为单会话语义后，`smoke-v3.js` 51 项全部通过。

## ADR-013：管理员认证与重启形态

- **管理员**：首次启动生成独立 RSA-2048 密钥对并打印随机初始口令；口令 PBKDF2-SHA256(12000 轮)，或 RSA-PSS 挑战签名登录（私钥不上传）；成功后签发 1 小时 token，全部管理接口强制校验。管理页本地内联 `assets/forge.min.js`，保证局域网 `http://` 非安全上下文下也能做签名。
- **重启**：管理页按钮采用**进程内软重启**（关监听 → 落盘 → 重建配置/密钥/DB/Hub/监听），端口不变、跨平台一致、不会因端口变化让管理页失联；未引入 `child_process`。换端口或升级代码仍需重启进程 / systemd 服务。
- **邀请码**：外层用共享口令派生密钥 AES-GCM + Base64URL，使客户端**离线**即可解出 IP/端口；内层附 HMAC（服务器归档主密钥派生），由服务端在 ROOM_JOIN 校验防伪。纯 HMAC 会让客户端无法预先得知服务器地址，故采用双层。

## ADR-014：v4 容量结论 —— 先做工程优化，不因「Rust 更快」而重写

- **实测**（`docs/11`）：每用户约 210 KB RSS / 88 KB Heap；单次注册 CPU 107.3 ms；归档 4～5 KB/条且 sql.js 全库常驻内存；大厅广播 36 µs/帧、复杂度 O(N²)；`node-forge` → `node:crypto` 可让注册握手快 24.7×。
- **决策**：2 核 4 G Ubuntu 26.04 上，调优后建议 800～1200 稳态在线（峰值 1500）。瓶颈是 fd 限制、归档内存、O(N²) 广播与纯 JS 大数运算，**不是 JavaScript 语言本身**；换 Rust/Go 而不改这三项，仍会卡在约 1000～1600。
- **取舍**：首选方案 A（Node 原地优化 + `node:crypto` + 归档滚动 + 2 进程 cluster，3～5 人日，3000～5000 在线，协议与客户端零变更）；仅在明确上万在线时考虑 Go（B）或 Rust（C）。本轮**只做评估与建议，未实施重写**，详见 `docs/12`。
- **前置运维项**：systemd `LimitNOFILE=65535`、归档滚动保留，二者与语言无关。

## ADR-015：免下载聊天采用门户引导，服务端绝不代管用户私钥

- **背景**：需求提出「服务端增加用户直接登录、导入用户信息 XML，无需下载客户端也可以聊天」。
- **事实**：`GET /` 本来就托管 `server/public/chatroom.html`，局域网浏览器直接访问即在线聊天；身份 XML 导入在纯浏览器里就能完成（File API → DOMParser → 可选 PBKDF2 解密 → RSA-PSS 挑战签名），服务端零改造。
- **决策**：新增 `/welcome` 门户页 + `/download/chatroom.html` + `/api/client-info`（含 SHA-256 与公钥指纹），把已有能力组织成清晰入口；把需求解释为「在服务端页面上直接登录聊天」。
- **明确否决**：让用户把 XML 上传到服务端、由服务端解密私钥代替注册（形态 C）。现有挑战签名正是为了证明私钥仍在用户手里；一旦上传，管理员可冒充该用户发起私聊，直接破坏 ADR-010 / ADR-011 的安全边界。详见 `docs/13`。

## ADR-016：机器人池只进入非 E2EE 房间

- **决策**：1000 个持久机器人身份写进 `identities`（`is_bot`）与身份哈希链；每 25 s 维持 10～20 个在线轮换；通过 `Hub.registerMessageHook()` 观察**普通房间**已归档消息并按概率自动回复；发言用 `room.key` 生成与真人一致的 AES-GCM 密文，走标准的 `handleEnvelope()` 归档/广播路径。
- **边界**：私聊房间 `room.key = null`，服务端本就没有明文密钥，机器人无法加入也无法旁听；管理员只能看私聊元数据（ADR-011 不变）。机器人使用 `BotSession`（不下发推送）、退出不广播 notice 且不写普通断开日志。
- **配置**：启停、池容量、在线上下限、刷新间隔、回复概率由 `/api/admin/bots*` 管理，写入 `bot_config` 链上区块并持久化，软重启后保留。

## ADR-017：多房间同开上限 3，移动端身份用浏览器内 Vault

- **多房间**：协议 `MAX_ACTIVE_ROOMS=3` + 错误码 `E_ROOM_LIMIT`；服务端在 ROOM_CREATE/ROOM_JOIN 前校验 `user.rooms.size`；客户端用 `openRooms[]` 与 `roomState{id}` 独立维护消息、成员、未读、历史，房间间广播与归档严格隔离。选 3 是「大厅 + 2 个房间」，兼顾需求与 O(N²) 广播的扇出成本。
- **移动端**：`100dvh` + `viewport-fit=cover` + `env(safe-area-inset-*)` + 16 px 输入框 + 抽屉侧栏 + 横向房间标签；局域网 `http://` 非安全上下文，**不做 Service Worker / WebAuthn**。
- **身份管理**：不依赖文件系统（浏览器无法静默写「当前目录」、iOS 下载路径不直观），改用 `localStorage` 身份库 `chatroom-identity-vault-v4`，支持导入/导出/重命名/删除/一键切换；加密身份的口令只存页面内存，不落盘。跨设备唯一可移植载体仍是导出 XML。

## v4 补充：测试脚本的可移植性修正

- 三个冒烟脚本原先硬编码 `server/data/admin-keys.json`，导致对**独立部署实例**（自生成管理员密钥）跑回归必然失败。改为支持 `CHATROOM_ADMIN_KEYS` / `CHATROOM_DATA_DIR` 覆盖。
- `smoke-test.js` 的 relay `clientId` 原为固定值 `smoke_relay_1`；relay 会话按 clientId 常驻服务端，连续第二次运行会在同一已注册会话上重复注册并报 `bad state`。改为每次运行生成唯一 id。
- 验证：仅含 `server/` 的独立目录换 8099 端口启动，`/api/health`、`/welcome`、`/`、`/admin` 全部 200，端到端 24/24 且可重复运行 —— ADR-009 的自包含结论在 v4 仍成立。

## ADR-018：身份链只记录持久化的正式用户

- **需求**：v5 要求「区块链中只有持久化的正式用户才会被保存，临时用户不存入区块链」。
- **决策**：在 `IdentityStore` 引入唯一判据 `_chainable(rec) = permanent && !isBot && uid 不以 'bot_' 开头`，所有链写入点（`register`、`verifyResume`、`setFlag`、`Hub.chainUserEvent`）统一改走该判据；房间创建、邀请发放等「用户动作」区块也只由正式用户触发。临时用户与机器人仍在 `identities` 表保留一行，用于在线管理、禁言与去重，但**不产生任何区块**。
- **理由**：临时身份每次登录都不同，写链只放大体积且无审计价值；机器人池 1000 条身份若写链会让链膨胀到无意义规模。链上区块稳定对应「可反复登录的真实身份」。
- **验证**：`smoke-v5.js` 记录链高，分别注册正式 / 临时用户后检查新增区块只含正式用户 uid，`/api/admin/ledger/verify` 仍返回 `ok: true`；`GET /api/state` 暴露 `chainPolicy: 'formal-users-only'`。

## ADR-019：大厅直聊不创建房间，用一次性密钥做 E2EE

- **需求**：「点击用户名私聊，不要建立房间，可以直接在大厅私聊」「要快速切换公聊和私聊状态」。
- **决策**：新增 `DIRECT_MESSAGE` / `DIRECT_MESSAGE_BROADCAST`，复用**当前房间（含大厅）**的成员集合与在线状态：发送方生成一次性 AES-256 密钥，用接收方公钥 RSA-OAEP 封装成 `wrappedKey`，密文连同 `iv/ct/tag` 交给服务端；服务端校验目标在线与同房间、`seq` 防重放、频率与长度，然后只把密文转发给接收方并按 `e2ee: true` 归档。
- **与 v3 E2EE 私聊房间的区别**：v3 的私聊房间是「双方专属房间 + 服务端不持房间密钥」；v5 大厅直聊是「不建房间 + 每消息独立密钥」。后者省去创建/邀请流程，符合「点击即私聊」，且服务端同样无法解密。
- **边界**：私聊不支持附件（文件链路复用房间密钥，与「仅接收方可解密」语义冲突）；更换身份文件后历史私聊密文不可解；管理员只能看到「[端到端加密内容，服务端不可解密]」。

## ADR-020：直聊使用独立 AAD 命名空间，禁止跨场景重放

- **决策**：客户端 `ChatCrypto.directAad(room, uid, seq, ts) = ['dm', room, uid, seq, ts].join('|')`，与公聊 `messageAad(room, uid, seq, ts) = [room, uid, seq, ts].join('|')` 不同；服务端归档私聊时写入同样格式的 `aad` 列。AES-GCM 把 AAD 纳入标签计算，因此公聊密文无法被当作私聊密文重放，反之亦然。
- **验证**：`verify-crypto-interop.js` 增加 10 项 v5 检查，覆盖 AAD 一致性、双向互通、公聊 AAD 解密失败、房间密钥解密失败、标签篡改被拒；`smoke-v5.js` 端到端验证第三方收不到密文、发送方不自收、不新增房间、归档仅 `e2ee` 标记、序号重放被拒。

## ADR-021：配置与版权采用服务端主动广播，而非客户端刷新

- **决策**：`name` / `copyright` / `copyrightLink` / `historyEnabled` / `maxRooms` / `maxMembersPerRoom` 属于展示态或即时策略配置。保存后 `Hub.broadcastServerConfig()` 向全部在线连接推 `SERVER_CONFIG_UPDATE`；房间改名推 `ROOM_UPDATED`；在线改名推 `NICKNAME_UPDATED`。客户端分别用 `applyServerBrand()` / `onRoomUpdated()` / `onNicknameUpdated()` 就地更新标题、房间标签、成员列表与底栏。
- **取舍**：端口与监听地址仍是启动参数（`/api/config/notes` 标为只读），需进程级重启；离线客户端下次登录时从 `REGISTERED` 回执获取最新值。不为展示态配置引入轮询或版本号，避免额外复杂度。
