# 单用户性能开销与容量规划（2 核 4 G / Ubuntu 26.04）

> 版本：v4 · 测量日期：2026-11-14
> 原始数据：`logs/benchmark-2026-11-14.json`，复现命令见文末。
> 测量对象：v4 基线服务端（Node v22.22.2、node-forge 纯 JS 加密、sql.js 内存数据库、单进程 ws）。

## 1. 测量方法

在隔离实例上跑 `CHATROOM_DATA_DIR` 独立数据目录，避免污染生产库：

```bash
CHATROOM_PORT=8099 CHATROOM_DATA_DIR=/opt/chatroom/.bench-data node src/main.js
CHATROOM_BASE=http://127.0.0.1:8099 node tools/benchmark.js --users 150 --messages 600
node tools/benchmark-crypto.js
```

服务端新增 `GET /api/metrics`（公开、不含任何密钥或消息内容），返回 `process.memoryUsage()`、`process.cpuUsage()`、V8 堆上限与 Hub 计数。脚本按 0/25/50/100/150 在线用户梯度采样，用**线性回归**求每用户内存斜率（避免 GC 抖动干扰），归档阶段按消息条数多次采样拟合，广播阶段轮询到全部消息落库为止才计时。加密原语另做微基准对比 `node-forge` 与 `node:crypto`。

> 本机为 Windows x64（Node v22.22.2），**未在真实 Ubuntu 26.04 实机测量**。Linux 上 epoll、glibc malloc 与 RSS 表现通常略优于 Windows，但同量级；下文容量结论按保守口径外推，并明确标注哪些是 Linux 特有约束。

## 2. 实测数据

### 2.1 单机基线

| 指标 | 实测 |
|---|---|
| 空载 RSS / Heap | 75.35 MB / 11.98 MB |
| 空载房间 / 身份 / 归档 | 1 / 0 / 0 |
| V8 堆上限 | 4144 MB（本机物理内存较大；**4 GB 机器上默认约 2 GB**） |
| 第三方依赖 | 全部纯 JS + WASM，无原生模块 |

### 2.2 每在线用户增量（连接 + 完成 RSA 注册，均在大厅）

| 用户数 | RSS | Heap |
|---|---|---|
| 0 | 75.63 MB | 9.28 MB |
| 25 | 77.48 MB | 13.33 MB |
| 50 | 87.41 MB | 15.04 MB |
| 100 | 89.91 MB | 14.26 MB |
| 150 | 109.77 MB | 26.11 MB |

线性拟合：**RSS +222.52 KB/用户**、**Heap +95.82 KB/用户**（R²=0.923）。首轮独立复测得 201.7 KB / 79.67 KB（R²=0.919），两次平均约 **210 KB RSS / 88 KB Heap 每用户**。

构成：`ws` 连接对象与收发缓冲区、每个用户的 RSA 公钥 PEM（约 450 B）、`user.rooms` / `lastSeq`、节流的会话状态、`usedNonces`、以及为该用户用其公钥 RSA-OAEP 封装的每个房间会话密钥。

### 2.3 单次注册（非对称握手）CPU

| 指标 | 实测 |
|---|---|
| 服务端 CPU / 次 | **107.3 ms** |
| 墙钟 / 次 | 184.27 ms（含网络与客户端侧） |
| 单核注册上限 | **约 9 次/秒**，2 核约 18 次/秒 |

微基准拆解（`tools/benchmark-crypto.js`）：

| 操作 | node-forge（纯 JS） | node:crypto（OpenSSL） | 加速比 |
|---|---|---|---|
| RSA-2048 OAEP 私钥解密 | 29.025 ms | 1.139 ms | 25.5× |
| RSA-PSS 验签 | 0.814 ms | 0.069 ms | 11.8× |
| AES-256-GCM 8 KB | 0.723 ms | 0.020 ms | 37× |
| 注册握手合计（解密+验签） | 29.84 ms | 1.21 ms | **24.7×** |

> 107.3 ms 大于微基准的 29.84 ms，因为一次注册还包含：解封混合密钥、写身份记录、向身份哈希链追加区块（**一次服务器 RSA-PSS 私钥签名**，约 29 ms）、以及大厅密钥的 RSA-OAEP 封装。也就是说**纯 JS 大数运算是 CPU 主要消耗**，与业务逻辑无关。

### 2.4 消息与归档

| 指标 | 实测 |
|---|---|
| 每条归档消息内存增量 | **3.738 KB/条**（600 条拟合，R²=0.616；保守按 **4～5 KB** 估算） |
| 600 条消息落库耗时 | 5.5 s（含客户端 45 ms 节流，非服务端上限） |
| 单条广播帧 | 约 300～350 B（iv/ct/tag/from/fromName/room/seq/ts） |

原因：sql.js 把**整个 SQLite 数据库常驻内存**，每条消息还要存 base64 密文、AAD、元数据和 B-tree 页；`db.export()` 落盘只是快照，不会释放内存。**归档无限增长是当前架构最危险的内存问题**（10 万条消息 ≈ 400～500 MB，100 万条即撑爆 4 GB）。

### 2.5 大厅广播 fan-out

| 指标 | 实测 |
|---|---|
| 在线用户 | 180 |
| 并发发送者 | 100 |
| 实际投递帧数 | 17 900（每条广播给 N−1 人） |
| 全部处理完成 | 640 ms |
| 服务端 CPU | 641 ms（≈ **36 µs/帧**） |

大厅广播是 **O(N²)**：每条消息要序列化并写给 `room.members` 中每个在线用户。这是稳态容量的第二道硬约束。

## 3. 2 核 4 G Ubuntu 26.04 容量推演

四个约束，取最小值。

### 约束 A：文件描述符（最容易被忽略的硬墙）

Ubuntu 26.04 上 systemd 服务默认 `LimitNOFILE` 常为 **1024**；每个 WebSocket 占 1 fd，加上监听、日志、WASM、数据库文件后，**约 1000 个连接就会报 `EMFILE`**。必须先设置：

```ini
# /etc/systemd/system/chatroom.service
[Service]
LimitNOFILE=65535
```

未调整时，**在线上限 ≈ 900**，与 CPU/内存都无关。

### 约束 B：内存

```
可用内存   4 GB − 系统/内核 0.5 GB − 预留 0.3 GB ≈ 3.2 GB = 3 355 MB
基线       75 MB
归档保留   按 2 万条 × 5 KB ≈ 100 MB（需实现滚动清理）
每用户     0.21 MB
→ (3355 − 75 − 100) / 0.21 ≈ 15 000 用户
```

V8 堆上限在 4 GB 机器上默认约 2 GB，按 Heap 88 KB/用户 ≈ 23 000 用户。**内存不是瓶颈**——前提是归档有上限；若不做归档清理，运行几天后会被归档吃满。

### 约束 C：CPU（稳态广播）

设每人每分钟发 `m` 条消息，全部在大厅：

```
帧率 = N × (N−1) × m / 60
可用 CPU ≈ 1.6 核（2 核留 20% 给系统/GC）
每帧 36 µs → 上限 ≈ 44 000 帧/s
```

| 在线 N | m=1 条/分 | m=2 条/分 | 结论 |
|---|---|---|---|
| 500 | 4 158 帧/s（0.15 核） | 8 317 帧/s（0.30 核） | 轻松 |
| 1 000 | 16 650 帧/s（0.60 核） | 33 300 帧/s（1.20 核） | 可用 / 接近上限 |
| 1 600 | 42 645 帧/s（1.54 核） | 85 290 帧/s（3.07 核） | 上限 / 不可行 |

**若用户被分散到多个房间**（每房间 30 人），广播范围从 N 降到 30，帧率变为 `N × 29 × m / 60`，N=10 000 时仅约 4 833 帧/s。**房间分片比换语言更有效**。

### 约束 D：注册风暴（非稳态）

2 核约 18 次注册/秒。服务端重启后 1000 个客户端自动重连，需要约 **56 秒**才能全部完成握手（客户端浏览器生成 RSA 密钥对还要额外耗时）。这不限制稳态在线数，但决定故障恢复体验。

### 约束 E：带宽

大厅 N=1000、每人 1 条/分钟 → 出向 `1000 × 999 × 320 B / 60 s ≈ 5.3 MB/s ≈ 42 Mbps`。千兆局域网无压力，百兆网络需降到 m≤0.5 或做房间分片。

## 4. 结论：能支撑多少在线用户

| 场景 | 建议在线上限 | 主约束 |
|---|---|---|
| **开箱即用（默认 ulimit、单大厅、无归档清理）** | **300～500 活跃用户 / 约 900 连接** | fd 1024、大厅 O(N²) |
| **基础调优后**（`LimitNOFILE=65535`、归档滚动保留 2 万条、引导用户分房间） | **800～1 200 稳态（含机器人），峰值 1 500** | 大厅广播 CPU |
| 全员只在大厅、每人 1 条/分钟 | 约 1 600 | CPU 上限 |
| 全员只在大厅、每人 2 条/分钟 | 约 1 100 | CPU 上限 |
| 原地优化（换 OpenSSL 原生加密 + 归档滚动 + 2 进程集群） | **3 000～5 000** | 内存/GC |
| Go 或 Rust 重写 + 磁盘型存储 + 房间分片 | **1 万～5 万** | 业务设计与网络 |

**直接回答**：以当前 v4 实现部署在 2 核 4 G Ubuntu 26.04，在**先调高 `LimitNOFILE` 并开启归档滚动清理**的前提下，稳定运行建议 **800～1 200 人在线**（轻度聊天，峰值 1 500）；若所有人都挤在大厅且发言活跃，上限降到约 **1 000～1 600**。内存层面可支撑上万，但 CPU 的 O(N²) 广播与注册握手先到顶。

## 5. 按性价比排序的扩容动作

| 优先级 | 动作 | 预期收益 | 成本 |
|---|---|---|---|
| P0 | systemd `LimitNOFILE=65535` | 解除 ~1000 连接硬墙 | 1 行配置 |
| P0 | 归档滚动清理（保留最近 N 条 / 按天淘汰） | 消除内存无限增长导致 OOM | ~0.5 人日 |
| P1 | 服务端 RSA/AES 改用 `node:crypto`（协议与密文格式不变） | 注册 CPU 降 ~25×，消息加解密降 ~37× | ~1 人日 |
| P1 | 引导分房间、限制大厅人数、按房间限流 | 把 O(N²) 降为 O(N×房间规模) | ~0.5 人日 |
| P2 | 身份链签名改 Ed25519 或批量签名 | 每注册省约 29 ms | ~1 人日 |
| P2 | Node `cluster` / 多进程 + 房间粘性路由 | 用满 2 核、隔离 GC 抖动 | ~3 人日 |
| P3 | 换 sql.js 为磁盘型 SQLite（`better-sqlite3`） | 归档不再占内存 | ~2 人日 + 原生编译 |

> 前四项做完，不换语言即可从 ~500 提升到 ~3000+。是否值得换 Rust/Go，见 `docs/12-语言与架构选型建议.md`。

## 6. 复现命令

```bash
cd D:/chatroom/server                    # Linux: /opt/chatroom/server
CHATROOM_PORT=8099 \
CHATROOM_DATA_DIR=/opt/chatroom/.bench-data \
CHATROOM_LOG_DIR=/opt/chatroom/.bench-logs \
node src/main.js

cd /opt/chatroom
CHATROOM_BASE=http://127.0.0.1:8099 node tools/benchmark.js --users 150 --messages 600
node tools/benchmark-crypto.js
curl -s http://127.0.0.1:8099/api/metrics
```

压测会写入大量归档行，**务必使用独立 `CHATROOM_DATA_DIR`**；该环境变量由 `server/src/paths.js` 统一管理，同时方便多实例部署。
